**Riders query was silently capped at 1000 rows, newest ones never loaded (2026-11-07): found and fixed, uncommitted.** A new self-registered rider wasn't showing up anywhere in `/admin` (not Apyrankės → Naudotojai, not Klientai) even after a hard refresh — not a staleness issue. `loadAdminData`'s `riders` query (`lib/admin/repository.ts:97`) ordered `created_at` ascending with no `.limit()`/`.range()`; Supabase's REST API caps every response at 1000 rows regardless of table size, and `riders` is 8,957 rows (ADR-0041's Grabby import). Confirmed directly against the live API: `order=created_at.asc` returns rows from 2022 with `Content-Range: 0-999/8957`; `order=created_at.desc` returns today's rows. So the admin dashboard had been silently loading only the **oldest** 1000 riders this whole time — every rider created since partway through the Grabby-import era, including every `/registracija` self-registration, was simply never in the dataset staff could search, full stop, no matter how they refreshed or what they typed. Fixed by flipping to `.order("created_at", { ascending: false })`, and `riders-tab.tsx`'s Naudotojai list now also explicitly sorts newest-first (`.toSorted` on `createdAt`) rather than trusting the incoming order. Also, while looking at a self-registered rider's profile, enlarged the header photo from a 40px circle to a 90×120px (3:4) rounded-lg portrait (`rider-page.tsx`) — a selfie cropped to a tiny circle was unreadable. `tsc`/eslint clean. **This is a stopgap, not the real fix** — bulk-loading all of `riders` into the client store doesn't scale past ~1000 rows either direction; the actual fix is server-side search/pagination for Klientai and Apyrankės's Naudotojai tab, not loading the whole table once at page load (see ADR-0041's addendum). Worth planning as its own piece of work once the current registration feature is settled.
